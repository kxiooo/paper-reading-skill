# Note Library — Problem 驱动的知识图谱更新

## 触发方式

当用户说 **"library"**，对当前讨论/ingest 完成的论文，按 **Problem 驱动**的方式更新 `_library/` 下的知识图谱。

> ⚠️ **路径注意**：`_library/` 在仓库根目录 `_library/`。

**前置条件**：论文必须已经被 ingest（笔记在 `_staging/notes/` 或 `_foundation/notes/` 中存在）。若尚未 ingest，先走 ingest 流程再回来更新库。

**核心链路**：`Problem → Failure Mode → Mechanism → Operator → Paper → Gap`

**入口**：所有更新从 `00-quick-query.md` 的总表出发——先判断这篇论文解决的是哪类问题，再层层挂接。

---

## 每次 library 必须回答的六问

对论文做库更新前，先在心里/草稿回答：

1. 它解决了什么问题？（在 `[[00-quick-query]]` 总表定位）
2. 为什么已有方法失败？（失败模式）
3. 这个问题属于哪类问题？（`1-problem-atlas` 节点）
4. 作者选择了什么机制？（`2-mechanism-atlas`）
5. 这个机制为什么适合？（机制 ↔ 问题的匹配理由）
6. 这个机制还能迁移到哪里？（跨领域迁移）

这六问是提取的纪律，不是要写进库里的长篇大论。

## 更新顺序（按此依次处理）

### 1️⃣ 问题挂接 → `1-problem-atlas.md`（必做）

判断论文解决的核心失败模式 → 挂到匹配的 `## Problem:` 节点下的「代表论文」表（wikilink + 怎么解决）。

- 已有问题节点 → 加一行（便宜）
- 全新失败模式 → 新建问题节点（用固定模板，昂贵，谨慎）
- 顺手更新该节点的 `Remaining Gap`（论文是否缩小了某个 Gap）

### 2️⃣ 机制提取 → `2-mechanism-atlas.md`（每篇必做）

从**底层算法本质**精炼 **2-3 个纯粹机制**。

**机制判据**（剥掉哲学外衣，看操作含量）：
- 机制 = 解决问题的**积木**：有明确步骤/输入输出，可被别的算法直接调用，剥掉哲学表述后仍有非平凡的操作细节（如预测-校正的缓存速度回溯、O(Δt³) 误差界）→ ✅ 进机制库
- 如果只是"相减/归一化"这类显而易见的通用运算，操作含量薄 → 它本质是**思想**，进 `4-thought-atlas`
- 如果只是某个具体方法名（"DDIM"、"MCM"）→ ❌ 不是机制
- 只要能跨领域解决不同问题 → ✅

**操作**：
- 已有机制 → 挂到对应节点，标注具体变体
- 全新机制 → 新建 `## 机制名` 节点（本质 / 能解决什么 / 变体 / 代表论文 / 能迁移到哪里）

### 3️⃣ 算子补充 → `3-operator-cookbook.md`（只有新算子才做）

判断论文是否引入了**新操作原语**（新的一类模块级操作，如 cross-attn / FiLM / mask / 子空间投影）。

- 只是已有算子的新组合 → ❌ 不更新（那是机制/问题层的事）
- 全新算子 → 在速查表加一行 + 详解小节

### 4️⃣ 思想提取 → `4-thought-atlas.md`（只有新母思想才做）

提炼论文背后的**母思想**（高维哲学范式）。

**思想判据**：是否是一种"观察问题的角度"而非"解决问题的技术"？
- Coarse-to-Fine ✅ → 策略哲学
- Diffusion Denoising ❌ → 具体技术
- 剥掉哲学外衣后，操作含量仍厚（非平凡）→ 它是机制，不是思想

**操作**：
- 匹配已有母思想 → 在二级思想下追加论文 + 远亲
- 全新母思想 → 新建 `## N. 母思想名` 节点，**必须**列 ≥3 个跨领域远亲论文

### 5️⃣ 分类提取 → `5-category-manifest.md`（每篇必做）

判断创新本质类型（主类 + 副类）→ 更新对应类别表 + 快速索引表。

- 🛠️ Method / 🎯 Task / 🧩 Representation / 🖐️ Interaction / 📐 Learning Paradigm / 🗺️ Survey

### 6️⃣ 数据方法论 → `6-data-methodology.md`（有条件才做）

判断是否用了**关于数据本身的方法**（造数据/找数据/筛选/增强/条件信号/外部记忆）。

- 有 → 挂到对应节点，标注具体做法
- **无 → 跳过此项**（不要硬塞）

---

## 维护铁律

- **只在有新增时才更新对应库**。论文行是廉价的（挂到已有节点），新节点是昂贵的（才新建）。
- 宁可少建节点，不要每次 ingest 都堆新结构——**降低维护摩擦，就是提高打开率**。
- 论文引用统一用：`[[_staging/notes/论文标题]]`
- 在已有节点下追加时，保持原格式不变；**禁止删除或覆盖已有内容**——只追加
- 新建节点后，在库顶部的目录/索引区顺手补上链接

## 与 `00-quick-query` 的联动

用户问研究问题时，**先查 `00-quick-query.md` 的总表**组织回答：
- 定位问题 → 跳 `1-problem-atlas` 看机制/论文/Gap
- 找 idea → 直接看 `1-problem-atlas` 底部「开放问题速查」
- 这不需要用户说"library"——是讨论时的自动行为
